# PostgreSQL Sequences

## 1. Technical Scope

This project examines PostgreSQL sequence objects and their use in relational database identifier generation.

It implements and compares four important approaches:

- Explicitly created sequences.
- `SERIAL` and `BIGSERIAL` pseudo-types.
- `GENERATED ALWAYS AS IDENTITY`.
- `GENERATED BY DEFAULT AS IDENTITY`.

The implementations demonstrate sequence allocation, session behavior, identifier management, ownership, caching, cycling, concurrency, and recovery after data imports.

The Python, JavaScript, C++17, and Java 17 programs implement executable sequence-management simulations. The PostgreSQL script implements the actual database objects and operations.

## 2. Sequence Fundamentals

A PostgreSQL sequence is a database object that generates successive numeric values.

Sequences are commonly used for:

- Primary-key generation.
- Transaction identifiers.
- Order numbers.
- Customer identifiers.
- Invoice references.
- Event and record identifiers.

A sequence maintains its own allocation state independently of ordinary table transactions.

A basic sequence can be represented as:

| Property | Purpose |
|---|---|
| `START WITH` | Initial value |
| `INCREMENT BY` | Difference between successive values |
| `MINVALUE` | Minimum permitted value |
| `MAXVALUE` | Maximum permitted value |
| `CACHE` | Number of values reserved in advance |
| `CYCLE` | Whether allocation restarts at a boundary |

An ascending sequence generally uses a positive increment. A descending sequence uses a negative increment.

### Sequence lifecycle

    Sequence Definition
           |
           v
    Configuration Validation
           |
           v
    NEXTVAL Allocation
           |
           v
    Identifier Assignment
           |
           v
    Table Insertion
           |
           v
    Sequence Monitoring

Sequence allocation and table insertion are separate operations. A successfully allocated value does not guarantee that the corresponding table record will be committed.

## 3. Explicit Sequence Objects

An explicit sequence provides direct control over identifier generation.

For example, `order_number_seq` is configured for order processing.

Its configuration includes:

- Starting value: 1000.
- Increment: 1.
- Minimum: 1000.
- Maximum: 999999999999.
- Cache: 1.
- Cycling: disabled.

A table can use the sequence through a column default.

The `nextval()` function obtains a new value and advances the sequence.

### NEXTVAL

`NEXTVAL` allocates a new sequence value.

Important characteristics:

- Allocation is atomic within PostgreSQL.
- Concurrent sessions can request values safely.
- Each successful allocation advances sequence state.
- A value is not returned to the sequence by an ordinary transaction rollback.

### CURRVAL

`CURRVAL` returns the last value obtained from a particular sequence by the current database session.

It requires an earlier `NEXTVAL` call on that sequence in the same session.

It does not return the most recently allocated value globally.

### LASTVAL

`LASTVAL` returns the last sequence value obtained through `NEXTVAL` in the current session, regardless of which sequence supplied it.

It is useful in limited session-specific workflows, but applications should generally use `INSERT ... RETURNING` to obtain the identifier associated with a particular inserted record.

### SETVAL

`SETVAL` changes the current sequence state.

Its third argument determines the behavior of the next allocation.

| Operation | Next NEXTVAL |
|---|---|
| `SETVAL(sequence, 500, TRUE)` | 501 |
| `SETVAL(sequence, 500, FALSE)` | 500 |

The increment is assumed to be one in this example.

For a sequence with another increment, the next value follows its configured increment.

`SETVAL` should be restricted to controlled maintenance operations because an incorrect reset can create identifier collisions.

## 4. SERIAL and BIGSERIAL

`SERIAL` and `BIGSERIAL` are PostgreSQL pseudo-types.

They provide convenient shorthand for creating an integer column with an associated sequence and a default expression.

| Type | Underlying column type |
|---|---|
| `SMALLSERIAL` | `SMALLINT` |
| `SERIAL` | `INTEGER` |
| `BIGSERIAL` | `BIGINT` |

A `SERIAL` declaration conceptually creates:

1. An integer column.
2. An associated sequence.
3. A column default using `NEXTVAL`.
4. Sequence ownership linked to the column.

The primary-key constraint is still separate and must be declared explicitly.

### Important distinction

`SERIAL` is not a genuine data type with special runtime storage behavior. It is shorthand for a set of database definitions.

It is useful in established PostgreSQL applications, particularly where compatibility with existing schemas is important.

## 5. GENERATED AS IDENTITY

Identity columns provide SQL-standard identity-generation functionality.

PostgreSQL supports two identity modes.

### GENERATED ALWAYS AS IDENTITY

This mode requires PostgreSQL to generate the identifier.

Ordinary explicit values are rejected.

An explicit value can be supplied through:

`OVERRIDING SYSTEM VALUE`

This is useful when importing controlled external data or migrating existing identifiers.

### GENERATED BY DEFAULT AS IDENTITY

This mode generates an identifier when an explicit value is not supplied.

A supplied identifier takes precedence over automatic generation.

It is useful in systems that combine normal application insertion with data migration and integration workflows.

### Comparison

| Property | SERIAL | ALWAYS | BY DEFAULT |
|---|---|---|---|
| Associated sequence | Yes | Yes | Yes |
| Automatic generation | Yes | Yes | Yes |
| Explicit values | Accepted | Restricted | Accepted |
| SQL-standard identity feature | No | Yes | Yes |
| Primary key automatic | No | No | No |
| Sequence synchronization after manual imports | Required when necessary | Required when necessary | Required when necessary |

Identity generation does not replace primary-key constraints.

A table should still define an appropriate primary key or unique constraint.

## 6. Sequence Ownership

Sequence ownership associates a sequence with a table column.

The PostgreSQL clause `OWNED BY` establishes this dependency.

Ownership is important because:

- It links the sequence lifecycle to the associated column.
- It supports dependent-object cleanup.
- It clarifies the relationship between identifier generation and table structure.
- It makes database schema inspection easier.

An independently created sequence without ownership can remain after its associated table is removed.

Identity columns have an automatically managed internal sequence.

Applications should use PostgreSQL's metadata functions instead of relying on assumptions about internal identity-sequence names.

## 7. Sequence Configuration and Behavior

### Increment

An increment determines the difference between successive values.

Positive increments create ascending sequences.

Negative increments create descending sequences.

A zero increment is invalid.

### Minimum and maximum

Boundary values constrain the permitted sequence range.

When a non-cycling sequence reaches its boundary, another allocation fails.

The application must handle this condition instead of assuming identifiers are unlimited.

### Cycling

A cycling sequence restarts from the opposite boundary when its limit is reached.

For ascending sequences, it returns to the minimum.

For descending sequences, it returns to the maximum.

Cycling introduces a critical limitation: values can be reused.

A cycling sequence is therefore unsuitable for a primary key that requires permanent uniqueness unless reuse is independently controlled.

### Cache

Caching allows PostgreSQL to reserve multiple sequence values for a session.

A larger cache can reduce allocation overhead in high-throughput workloads.

The trade-off is that unused cached values may be lost when a session disconnects or a database failure occurs.

Cached sequence allocation does not guarantee gap-free identifiers or a globally continuous order of observed values.

## 8. Non-Transactional Sequence Behavior

One of the most important sequence properties is that sequence allocation is not rolled back with ordinary transactional changes.

Consider this workflow:

    BEGIN
       |
       v
    NEXTVAL = 100
       |
       v
    INSERT RECORD
       |
       v
    TRANSACTION FAILURE
       |
       v
    ROLLBACK
       |
       v
    NEXTVAL = 101

The identifier 100 remains consumed even though the inserted record is absent.

This behavior is intentional.

PostgreSQL prioritizes efficient concurrent sequence allocation rather than transactional, gap-free numbering.

Consequences include:

- Gaps after failed inserts.
- Gaps after transaction rollbacks.
- Gaps when cached values are abandoned.
- Gaps after application errors.
- Gaps when identifiers are allocated but never inserted.

A sequence is therefore suitable for surrogate identifiers but not for enforcing legally gap-free business numbering.

If a business process requires controlled document numbering, that requirement needs a separate transactional design with appropriate locking, uniqueness rules, and audit controls.

## 9. Concurrency and Session Isolation

PostgreSQL supports concurrent sequence access.

Multiple database sessions can execute `NEXTVAL` without receiving the same allocation from a non-cycling sequence under normal operation.

The database manages sequence allocation internally.

The programs demonstrate this through synchronized allocation models and concurrent worker execution.

### Session-specific state

`CURRVAL` is maintained separately for each session.

For example:

| Session | Allocated value | CURRVAL |
|---|---:|---:|
| Session A | 101 | 101 |
| Session B | 102 | 102 |
| Session A | 103 | 103 |
| Session B | 104 | 104 |

Session A does not obtain Session B's current value through `CURRVAL`.

For application code, `INSERT ... RETURNING` is generally the clearest method of retrieving the identifier generated by an insertion.

## 10. Sequence Synchronization

A common operational problem occurs during bulk imports.

Suppose a table already contains manually imported identifiers:

| Customer ID |
|---:|
| 100 |
| 200 |
| 5000 |
| 9000 |

If its associated sequence still generates values beginning at 1, future inserts can conflict with existing records.

The sequence must be synchronized.

PostgreSQL provides `setval()` and `pg_get_serial_sequence()` for this purpose.

The demonstration SQL includes a synchronization function that:

1. Locks the target table against conflicting data modifications.
2. Determines the maximum existing identifier.
3. Retrieves the associated sequence.
4. Sets its state to the maximum identifier.
5. Returns the synchronized value.

The operation requires careful coordination with application writers.

Sequence synchronization is a maintenance operation, not a substitute for primary-key constraints.

## 11. Python Implementation

The Python program models sequence behavior through dedicated classes and data structures.

### Main components

| Component | Responsibility |
|---|---|
| `SequenceConfig` | Immutable sequence configuration |
| `PostgreSQLSequence` | Allocation and sequence state |
| `CustomerIdentityTable` | Identity-column behavior |
| `TransactionSimulator` | Rollback demonstration |
| `SequenceSnapshot` | Sequence reporting |
| `IdentityMode` | Generation policy |
| `SequenceLimitError` | Boundary failure handling |

### Implementation decisions

The sequence class uses `threading.Lock` to protect allocation state.

A dictionary stores session-specific current values.

The `nextval()` method performs an atomic state transition inside the simulator.

The `setval()` method distinguishes between a called and an uncalled sequence state.

The customer table validates names, email addresses, and primary-key uniqueness.

The reporting functionality exports sequence information as JSON.

### Important limitation

The Python program is a behavioral simulator, not a PostgreSQL client.

Its lock protects only threads within the running Python process. It does not reproduce PostgreSQL's distributed session management, WAL behavior, server-side sequence caching, or database persistence.

The PostgreSQL SQL implementation demonstrates those actual database mechanisms.

## 12. JavaScript Implementation

The JavaScript implementation provides an asynchronous sequence-management model.

### Main components

| Component | Responsibility |
|---|---|
| `SequenceManager` | Sequence lifecycle and allocation |
| `IdentityTable` | Identity-based record creation |
| `TransactionSimulator` | Transaction failure modeling |
| `SequenceError` | General operation errors |
| `SequenceLimitError` | Boundary enforcement |
| `SequenceConfigurationError` | Configuration validation |
| `EventEmitter` | Allocation event monitoring |

### Event-driven behavior

The sequence manager emits events after successful allocations.

Monitoring components can subscribe to these events.

This creates a separation between identifier allocation and operational monitoring.

### Asynchronous allocation

A promise queue serializes sequence mutations within the Node.js process.

Concurrent callers can request identifiers through asynchronous methods.

`Promise.all()` is used to coordinate multiple worker tasks.

### Implementation limitation

The JavaScript queue models process-local coordination. It does not provide the cross-process or cross-server guarantees of PostgreSQL sequences.

The `cache` configuration is retained as metadata in this implementation; it does not implement PostgreSQL's server-side cache reservation mechanism.

JavaScript's safe-integer limitation also means that this implementation does not represent the complete signed 64-bit PostgreSQL `BIGINT` sequence range.

## 13. C++17 Implementation

The C++17 program models sequence allocation in a concurrent order-processing environment.

### Main components

| Component | Responsibility |
|---|---|
| `SequenceConfig` | Sequence configuration |
| `PostgreSQLSequence` | Allocation and state management |
| `CustomerTable` | Customer identifier management |
| `TransactionSimulator` | Non-transactional behavior |
| `Customer` | Domain record |
| `IdentityMode` | Identity-generation policy |

### Concurrency

The sequence uses `std::mutex` to protect shared allocation state.

Multiple worker threads request identifiers concurrently.

Each worker collects values locally before updating the shared results collection.

The program checks the resulting set for duplicate values.

This approach separates allocation synchronization from result aggregation.

### Failure handling

The program uses exceptions for:

- Invalid sequence configuration.
- Invalid session identifiers.
- Sequence exhaustion.
- Duplicate customer identifiers.
- Invalid customer data.

The implementation also handles arithmetic boundary conditions before advancing the sequence.

### Complexity

For a sequence allocation, the simulator performs constant-time state updates under a mutex, excluding contention and synchronization overhead.

Session-value lookup uses an `unordered_map`, with average constant-time lookup.

Customer lookup and insertion also use hash-based storage.

The concurrent test performs 800 allocations across eight workers.

## 14. Java 17 Implementation

The Java program models an enterprise customer-management workflow.

It separates sequence configuration, ownership, customer services, monitoring, and transaction simulation.

### Main components

| Component | Responsibility |
|---|---|
| `SequenceConfig` | Validated sequence settings |
| `PostgreSQLSequence` | Allocation and session state |
| `CustomerService` | Customer creation and validation |
| `SequenceOwnershipRegistry` | Sequence ownership rules |
| `SequenceMonitoringService` | Operational reporting |
| `TransactionSimulator` | Failure and rollback modeling |
| `SequenceObserver` | Allocation-event interface |
| `SequenceReport` | Immutable monitoring data |
| `Customer` | Immutable customer record |

### Enterprise design decisions

Java records provide immutable representations of sequence configurations, allocation events, reports, and customer records.

The observer interface separates sequence operations from monitoring.

The ownership registry ensures that a sequence cannot be assigned to conflicting owners within the simulator.

The customer service validates identity policies before creating records.

The executor service runs concurrent allocation tasks.

`Math.addExact()` detects arithmetic overflow.

### State transitions

A non-cycling sequence transitions from `READY` to `EXHAUSTED` when its boundary is reached.

The implementation reports the resulting state and rejects further allocations.

The model uses synchronized methods for process-local state protection.

It does not reproduce PostgreSQL persistence or server-side locking.

### Trigger behavior

The order-insertion trigger records successfully inserted order identifiers.

It does not record every sequence allocation.

A failed insertion or rolled-back transaction can consume a sequence value without creating a corresponding audit record.

This distinction is important when designing audit systems.

### Performance considerations

Indexes are provided for order creation time and order status.

Sequence caching is demonstrated independently.

Increasing cache size can improve allocation performance, but it also changes how unused reserved values may be lost.

The appropriate cache size depends on workload characteristics, availability requirements, and operational recovery policies.

## 16. Security and Operational Controls

Sequences are database objects with their own privileges.

Access to a table does not automatically imply unrestricted access to its associated sequence.

PostgreSQL sequence privileges include:

| Privilege | Purpose |
|---|---|
| `USAGE` | Allows sequence usage operations such as `NEXTVAL` |
| `SELECT` | Allows reading sequence state and using `CURRVAL` |
| `UPDATE` | Allows sequence modification, including `SETVAL` |

Production systems should follow least-privilege access.

Application roles should not receive unnecessary sequence modification privileges.

Sequence reset operations should be limited to trusted maintenance roles.

Other operational controls include:

- Protecting ownership and schema permissions.
- Avoiding uncontrolled manual identifier insertion.
- Monitoring sequence exhaustion.
- Validating imports before synchronization.
- Maintaining primary-key constraints.
- Coordinating maintenance with application writers.
- Avoiding exposure of sensitive business information through identifiers.

Sequence-generated identifiers are not authentication credentials or authorization tokens. Their numerical unpredictability should never be treated as a security control.

## 17. Important Edge Cases

| Scenario | Expected behavior |
|---|---|
| NEXTVAL called repeatedly | New values are allocated |
| CURRVAL before NEXTVAL | Error |
| CURRVAL from another session | Error if that session has not called NEXTVAL |
| SETVAL with `TRUE` | Next value advances from the supplied value |
| SETVAL with `FALSE` | Next value equals the supplied value |
| Transaction rollback | Sequence allocation remains consumed |
| Failed insertion | An allocated value may be lost |
| Maximum reached without CYCLE | Further allocation fails |
| Maximum reached with CYCLE | Sequence restarts at minimum |
| Descending sequence reaches minimum | Further allocation fails or cycles |
| Manual identifier import | Sequence may require synchronization |
| Duplicate identifier | Primary-key constraint rejects insertion |
| Cache abandoned | Unused reserved values may be lost |

## 19. Engineering Limitations

The four general-purpose language implementations simulate sequence behavior rather than directly communicating with a PostgreSQL server.

They provide useful models for understanding allocation, state, concurrency, identity policies, and failure handling.

They do not reproduce all PostgreSQL implementation details.

| Feature | Python | JavaScript | C++17 | Java 17 | PostgreSQL |
|---|---|---|---|---|---|
| Allocation simulation | Yes | Yes | Yes | Yes | Actual |
| Session model | Yes | Yes | Yes | Yes | Actual |
| Identity policies | Yes | Yes | Yes | Yes | Actual |
| Concurrent allocation | Thread lock | Promise queue | Mutex | Synchronization | Database-managed |
| Persistent sequence state | No | No | No | No | Yes |
| Server-side cache | No | No | No | No | Yes |
| Transaction integration | Simulated | Simulated | Simulated | Simulated | Actual |
| Database ownership | Simulated | Not implemented | Not implemented | Simulated | Actual |
| Database privileges | Not implemented | Not implemented | Not implemented | Not implemented | Actual |

The PostgreSQL implementation is authoritative for actual database behavior.

## 20. Practical Design Principles

1. Use `IDENTITY` for new PostgreSQL schemas requiring standard identity-column behavior.
2. Retain `SERIAL` where existing application compatibility makes migration unnecessary.
3. Use explicit sequences when identifier allocation requires independent configuration or direct reuse.
4. Define primary-key and unique constraints independently of identifier generation.
5. Use `INSERT ... RETURNING` to retrieve generated identifiers reliably.
6. Expect gaps in generated identifiers.
7. Do not use cycling sequences for identifiers requiring permanent uniqueness.
8. Synchronize sequences after controlled bulk imports.
9. Protect sequence-reset operations through database privileges and maintenance procedures.
10. Select sequence cache settings according to actual workload and failure-recovery requirements.

The essential architectural distinction is that a sequence generates numeric values, an identity or default expression connects those values to a table column, and a primary-key constraint enforces relational uniqueness.
